# 顔認識による人物別アルバム

写真.app の顔認識を使い、特定の人物（config.json の person で指定）が写った写真だけを集めたアルバムとフォルダを作る。みてねなど他サービスへアップロードする際に、791枚から探す手間をなくすのが目的。

実行は [export_person.py](../export_person.py)。1日4回のジョブ（`run_person_tasks.py`）に組み込み済み。本体(17:30)からも呼ばれる。

**判定の実装は [common.py](../common.py) の `person_photo_candidates()` にある。** `export_person.py` と `mitene_upload.py` が同じSQLを別々に持っていた時期があり、片方だけ直すと「アルバムには入るのにみてねには上がらない」という食い違いが静かに起きる状態だった。判定を足す・変えるときは必ずここを直すこと。

## 結果（2026-08-27 時点）

| | 枚数 | 割合 |
| --- | --- | --- |
| コドモンアルバム全体 | 792 | — |
| 人物が検出された写真 | 784 | — |
| 指定した人物が検出された写真 | 180 | 22.7% |
| **うち採用（顔が検出されているもの）** | **152** | **19.2%** |

検出は全体で2,855個。うち対象人物は185個（6%）で、残りは園の他の子どもたち。
対象人物の185個のうち32個は顔ではなく胴体のみの検出で、採用していない（後述）。

### 識別率が22%に留まる理由

**画像が500px上限だから**。顔の幅の中央値は33pxしかなく、本人判定の実用下限とされる60pxを超えるのは21%だけだった（Vision frameworkで実測）。この21%という数字が識別率22.1%とほぼ一致しており、**解像度がそのまま識別率の上限になっている**。

アルゴリズムを変えても改善は見込めない。原寸を得るには「写真共有・販売」の購入が必要（[01-api.md](01-architecture.md) 参照）。

## 胴体だけで同定された写真は採用しない

写真.app は**顔が見えない人物を、体つきと服装から同定する**（`ZDETECTEDFACE` に行はできるが顔ではない）。園全体の引き写真で頻発し、「子どもの顔が写った写真を家族に送る」という目的には合わないため採用しない。

見分け方は `ZSIZE`。

| 列 | 通常の顔検出 | 胴体のみ |
| --- | --- | --- |
| `ZSIZE` / `ZCENTERX` / `ZCENTERY` | 値が入る | **すべて 0** |
| `ZQUALITY` | 0〜1 | **-1（未測定）** |
| `ZBODYWIDTH` / `ZBODYHEIGHT` | 入らない | **値が入る** |
| 年齢・表情・視線などの顔属性 | 入る | **すべて空** |
| `ZDETECTIONTYPE` | 1 | **1（同じ。見分けには使えない）** |

`ZDETECTIONTYPE` は両者とも 1 なので判別に使えない。**`ZSIZE > 0` で絞ること。**

2026-08-27 時点の実測では、コドモンアルバム内の検出2,855個のうち **1,389個（49%）が胴体のみ**。「対象人物」に限ると185個中32個で、**写真枚数では180枚中28枚**がこれだけを根拠に選ばれていた。実物を確認するとすべて保育室全体の引き写真だった。

## 顔の大きさと主役度で絞る

`person_photo_candidates()` は各写真について次を測り、`Thresholds.judge()` で採否を決める。

| 値 | 意味 |
| --- | --- |
| `face_px` | その人物の顔の幅。`ZSIZE × 画像の幅` の実ピクセル |
| `face_ratio` | 写真内で最大の顔に対する比。1.0 ならその人物が最大 |
| `faces` | 写真内の検出数（顔＋胴体） |

判定式は次のとおり。閾値は `config.json` で調整できる（`face_min_px` / `face_main_ratio` / `face_max_people`）。

```text
採用 =  (face_px >= face_min_px かつ face_ratio >= face_min_ratio)
     or (face_ratio >= face_main_ratio かつ faces <= face_max_people)
```

```bash
.venv/bin/python3 export_person.py --explain   # 閾値と1枚ずつの評価を表示（何も変更しない）
```

### 絶対サイズと主役度は別のことを測っている

| | 分かること | 分からないこと |
| --- | --- | --- |
| `face_px` | 顔が判別できる大きさか | 引きで全員小さいのか、本人だけ小さいのか |
| `face_ratio` | 写真内で主役か | そもそも顔が見える大きさか |

片方だけでは足りない。実例として `example-photo-A`（22px・比0.60）は顔幅では `example-photo-B`（18px・比1.00）より大きいが、実際は別の子が主役で本人は脇にいる。前者は比で、後者は顔幅で落ちる。

### 絶対サイズだけだと「手前の子が主役」の写真が通る

`face_min_ratio` は、顔が十分大きくても脇役なら落とすための下限。手前の子を大きく写した写真では、後ろにいる本人の顔も十分な画素数になるため、絶対サイズだけでは弾けない。

実例が `example-photo-C`。給食の写真で、手前の子がピースをしてカメラを向いている。

| | 顔幅 | 比 | 位置 |
| --- | --- | --- | --- |
| 手前の子 | 108px | 1.00 | 中央 |
| **対象人物** | **53px** | **0.49** | 左端・横顔（yaw -0.98） |

対象人物の顔は53pxあり `face_min_px=25` を余裕で超えるので、下限が無いと採用されてしまう。**他人の顔が2倍以上大きければ脇役**とみなして落とす。

`face_min_ratio=0.6` で落ちるのは5枚（0.42〜0.57）で、5枚とも実物を確認して「本人は背景側」だった。0.5だと上記の0.49がぎりぎりで、余裕を見て0.6にしている。

なお、この5枚のうち3枚は `ZPOSEYAW` の絶対値が1.0前後（＝横顔）だった。横顔を直接弾く手もあるが、比の下限で足りているため使っていない。

### 比による救済は集合写真を拾ってしまう

**整列した集合写真は全員の顔が同じ大きさなので、比が 1.0 に近づく。** 実測では `face_min_px=25` に対する比1.00の救済10枚のうち、2人だけの写真は1枚で、残り9枚は5〜10人が並んだ写真だった。比を 0.80 まで下げると救済は30枚に増えるが、うち8人以上の集合写真が14枚を占める。

比だけで主役度を測ると必ずこれを拾うため、救済に使うときは `face_max_people` で人数の上限を併用する。

**採用した設定は `min_px=25` / `min_ratio=0.6` / `main_ratio=0.8` / `max_people=5`。** 比を 1.0 から 0.8 まで緩めて少人数の引き写真を拾いつつ、人数の上限で集合写真の流入を止める組み合わせ。集合写真そのものが不要なわけではないが、それは「対象人物の写真」として送るものではないという整理。

| 設定 | 採用 | 内訳 |
| --- | --- | --- |
| `min_px=25` のみ | 97枚 | 比による救済なし |
| `min_px=25` / `ratio=1.0` / 人数無制限 | 107枚 | 救済10枚のうち9枚が集合写真 |
| `min_px=25` / `ratio=0.8` / 人数無制限 | 127枚 | 救済30枚のうち14枚が8人以上 |
| `min_px=25` / `ratio=0.8` / `max_people=5` | 104枚 | 救済7枚。少人数の引き写真だけが残る |

実測（対象人物・152枚）では顔幅の中央値は 31.1px、**写真内で最大の顔なのは76枚だけ**だった。残りは他の子が主役の写真ということになる。

### `ZSIZE` は「画像の幅」に対する比（長辺ではない）

縦位置の写真（500x667）で長辺を掛けると **1.33倍に水増しされる**。`ZCENTERX`/`ZCENTERY` が軸ごとに正規化されている（`ZCENTERY` は下端が0）のと同じで、`ZSIZE` は x 軸すなわち幅に対応する。

検証は切り出しで行った。縦位置の写真について幅基準（83px）と長辺基準（111px）の枠を実際に切り出して比べ、さらに横位置の写真（幅と長辺が一致するので基準の差が出ない）の枠と見比べたところ、**幅基準の枠だけが横位置と同じ「目から口まで」の収まり**になった。`ZSIZE` の枠は髪や顎を含まない内側の顔領域で、実際の顔幅の 6 割ほどにあたる。

配信画像は幅がつねに 500px なので、実質 `face_px = ZSIZE × 500` になる。

## アルバムは追記専用ではなく、作り直して揃える

写真.app の AppleScript は**アルバムから写真を外せない**。そのため以前は、判定が変わっても一度入った写真が残り続けた（実際に、写真.app側の再クラスタリングで「対象人物」ではなくなった2枚がアルバムに残っていた）。

一方 `delete` は**アルバムとフォルダには使える**（`Only albums and folders can be deleted.`）。`name` プロパティも書き換えられる。そこで、アルバムに対象外のものが混ざっているときだけ次の手順で作り直す。

1. 一時アルバム `コドモン（対象人物）_rebuild` を作る
2. 正しい集合を `add` する
3. **枚数を数えて確認してから**、旧アルバムを `delete`
4. 一時アルバムを本来の名前へリネーム

削除を最後に置くのは、途中で失敗しても旧アルバムを失わないため。枚数が足りなければ中止して旧アルバムを残す。混ざりが無いときは単純な追記で済ませる（毎回作り直すと iPhone 側でアルバムが消えて再出現するため）。

**アルバムを作り直しても写真の実体は減らない。** アルバムは参照の集合なので、ライブラリのアセット数もiCloudの使用容量も変わらない。

採用写真が0枚になった場合も、既存の人物アルバムを空にして判定結果に揃える。`--person` で設定と異なる人物を指定すると、その人物名から出力アルバム名を作る。設定済みの人物用アルバム名は既定人物にだけ適用し、出力先を明示したい場合は `--album` を使う。

## 顔解析はいつ実行されるか

**取り込み直後には解析されない。** macOSの `photoanalysisd` が、Macが電源接続かつアイドルのときに少しずつ進める。

実測では、680枚を取り込んだ直後は10枚しか解析されておらず（`photoanalysisd` のCPU時間は2時間で5秒）、一晩放置して全680枚が完了した。

このため**新着写真がすぐ人物アルバムに入ることはない**。数時間〜数日遅れる。

### 日付ベースの処理にしてはいけない

「前日ダウンロードした分を処理する」という設計だと、その時点では未解析なので取りこぼし、その後解析されても二度と見に行かない。

`export_person.py` は**毎回全期間を再評価**し、アルバムに無いものだけ追加する。解析がいつ完了しても次の実行で拾われる。全期間評価でも3〜4秒で終わる。

## 出力

| 出力先 | 内容 |
| --- | --- |
| 写真.app人物別アルバム | 該当写真のアルバム。iCloud経由でiPhoneからも見られる |
| `~/Pictures/codomon-person/` | 同じ写真のローカルコピー。**定期実行では `--no-copy` を渡すため更新されない**（手動で `export_person.py` を引数なしで実行したときのみ） |

### アルバムに入れても写真は二重にならない

アルバムは**写真の実体ではなく参照の集合**。153枚を2つ目のアルバムに入れても、ライブラリのアセット数（8,304）も容量（21G）も変化しないことを実測で確認済み。iCloudの使用容量も増えない。

ただし**AppleScriptの `import` は使ってはいけない**。`import` は新規取り込みなので実体が増える。既にライブラリにあるアイテムを `add` でアルバムに参照登録すること。

## 制約

**iCloud共有アルバムへの自動投稿はできません。** AppleScript・PhotoKit・ショートカットのいずれからも書き込めず、投稿するとファイル名も日時も変わるため送信済みの判定もできません。検討のうえ不採用としました。

**写真.appの操作には制限があります。** AppleScript から写真の削除やアルバムからの除外はできません。アルバム内の重複を解消したい場合は、重複を除いた新しいアルバムを作って入れ替えます（ライブラリの写真は削除せずに済みます）。

**フルディスクアクセスが必要です。** 顔認識の結果は写真.appのライブラリDBから読むため、実行元にフルディスクアクセスを与えてください。
付与できているかは `python3 setup.py doctor` で確認できます（実際にDBを開いて判定します）。

**`config.json` の `person` が空なら、顔認識は動かずエラーにもなりません。** 顔認識を使わない構成も想定した設計です。
